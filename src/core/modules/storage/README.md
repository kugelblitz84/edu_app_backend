# Storage provider integration

Import StorageModule and inject StorageProvider. Profile pictures and study materials implement their own purpose/owner-bound pending upload, inspection and completion flows; there is no generic unprotected file-ID-to-media controller. [Study materials API](../../features/Resources/README.md) documents direct uploads, delivery and durable cleanup. [Profile pictures](../../features/user-profile/README.md) retain their existing behavior and 5 MiB cap.

Configure CLOUDINARY_API_KEY, CLOUDINARY_API_SECRET, CLOUDINARY_CLOUD_NAME and CLOUDINARY_UPLOAD_PRESET for the deployment. The preset must be **signed**, allow jpg,png,webp,mp4,pdf, use authenticated delivery, and disable overwrites. Do not enable incoming format conversion, public-ID rewriting or folder prefixes. The service signs the preset and per-request allowed format. Configure the account before uploads; application code does not change account settings.

CLOUDINARY_MAX_UPLOAD_BYTES defaults to 10485760 (10 MiB), constraining PDFs and videos as well as images. The effective resource limit is the smaller of the purpose-specific feature cap and this provider cap. Raising it preserves the separate 5 MiB profile picture cap. Cloudinary presets do not enforce a custom per-preset byte limit; configure account-level usage limits where available. Server validation rejects oversized declarations/verified metadata but cannot prevent a dishonest client transmitting larger bytes before completion. Large-video chunking is not implemented. See [upload presets](https://cloudinary.com/documentation/upload_presets).

The allowlist is JPEG, PNG, WebP, MP4 and PDF. Server mapping chooses resource type, extension and folder. Raw PDF IDs retain .pdf; image/video IDs omit extensions. Exact locator, delivery type, format and provider-reported bytes are inspected at completion. This is metadata validation, not malware scanning or proof of safe PDF contents.

1. Persist application fileId, exact expected MIME/bytes, actor, purpose, target, pending reference and expiry before returning a sanitized descriptor.
2. The client posts returned multipart fields plus file directly to the provider URL. Signed upload fields necessarily include provider parameters; application completion still accepts only application fileId and concurrency data, never client locators/provider responses.
3. Load the stored reference, reauthorize actor/target, inspect outside a database transaction, compare exact size, then recheck state/expiry/permissions and activate transactionally. Persist the verified reference only server-side. Failed replacement retains current content; replaced files remain recorded until cleanup succeeds.
4. Authorize the exact resource/collection context on every read and pass the verified reference to createReadAccessUrl. Metadata does not contain full-content URLs. Image delivery also checks attachment relationship/purpose. StorageError is translated without exposing provider responses.

The current adapter uses Cloudinary private_download_url with authenticated type, inline disposition and 900-second expiry. Upload signatures last 3600 seconds. All descriptor expiresAt values use Unix seconds. These API delivery links bypass CDN caching and incur a bandwidth tradeoff ([Cloudinary access controls](https://cloudinary.com/documentation/control_access_to_media#providing_time_limited_access_to_private_media_assets)); they are not a claim of CDN streaming. Ordinary signed transformation URLs do not enforce the same expiry and are not used as a replacement.

Real-account MP4 seeking, PDF rendering, byte ranges, content type, CORS and expiry/refresh remain deployment acceptance checks; the [API manual verification steps](../../features/Resources/README.md#required-real-providerbrowser-verification-outstanding) specify them. If a configured account cannot deliver required behavior, implement/test that capability behind StorageProvider before releasing it. Never replace expiring links with permanent public URLs.

Read authorization is rechecked before every newly issued URL. A previously issued bearer URL can remain usable for its remaining 15-minute lifetime after enrollment/grant revocation, PIN rotation or state change. Already delivered bytes cannot be revoked. Signed responses use private/no-store and should not be logged. Deletion is idempotent. Materials cleanup is durable, retries across instances and waits until the upload signature window plus grace, with a follow-up pass for late uploads; the profile picture implementation remains separate.
